# Агрегатор новостей и вакансий

Автоматический сервис: собирает материалы из публичных RSS и API, нормализует их,
дедуплицирует, складывает в SQLite и присылает дайджест в Telegram — по расписанию
или по команде в боте.

Учебный проект по вайб-кодингу (уровень ⭐⭐⭐). Заказчик — компания, которая ежедневно
мониторит новости отрасли, вакансии, обновления технологий и публикации конкурентов.

```
Источники → Сборщик → Нормализация → Дедупликация → SQLite → Отбор → Дайджест → Telegram
```

## Что умеет

- **9 включённых источников** (RSS, REST API, GitHub API) в четырёх разделах; список задаётся
  конфигом, а не кодом.
- **Дедупликация по `dedup_hash`**: нормализация URL (utm-метки, фрагмент, схема, `www`,
  завершающий слэш, сортировка параметров) плюс фолбэк на `title + source`.
- **Метки вместо жёстких разделов**: заголовки и эмодзи разделов живут в `config/labels.yaml`,
  в коде нет ни одной строки вида «📰 Новости отрасли».
- **Глубина проверки** (`lookback_days`) применяется на каждом запуске, а не только на первом:
  остановили сервис, запустили снова — окно то же, дублей нет.
- **Три этапа фильтрации**: параметры запроса к API → жёсткие `item_filters` (зарплата «от/до»,
  регион) → тематические `keywords`/`exclude` при сборке дайджеста.
- **Telegram-бот** как единственный интерфейс: команды, ручной дайджест, статус, пауза.
- **Планировщик** APScheduler с cron-выражением у каждого раздела.
- **Опциональное саммари** через DeepSeek.

## Быстрый старт

```bash
python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                              # заполнить токен бота, chat_id, ключи
python main.py --check                            # проверить конфиг и схему БД
python main.py --collect                          # собрать материалы один раз
python main.py --digest                           # собрать и отправить дайджест
python main.py                                    # сервис: бот и планировщик вместе
```

Полезные режимы:

| Команда | Что делает |
|---|---|
| `python main.py --check` | валидация конфигурации и схема БД, ничего не запускает |
| `python main.py --collect [--source ID] [--lookback-days N]` | только сбор, с таблицей `fetched/new/dup/filtered` |
| `python main.py --digest [--label X] [--no-collect]` | дайджест и отправка (при `DRY_RUN=1` — печать в консоль) |
| `python main.py` | сервисный режим: `run_on_start` + cron + бот |

### Перевод иностранных источников

У источника в `sources.yaml` есть необязательное поле `translation` — код языка оригинала
(ISO 639-3, принимаются и двухбуквенные: `eng`/`en`, `deu`/`de`). Если поле задано,
заголовок и описание переводятся **при сборе**, и в базе материал сразу на русском:

```yaml
  - id: hackernews
    type: api
    label: tech
    translation: eng        # нет DEEPSEEK_API_KEY — перевод молча выключен
```

Что важно знать:

- переводятся **только новые** материалы и только после дедупликации: на каждом прогоне
  новыми бывают единицы из десятков полученных, остальные — повторы, и за них платить
  не нужно (повторный сбор Hacker News: 1.1 с вместо 30.6 с);
- в модель уходят **только заголовок и короткое описание** — полных статей проект не
  скачивает (у Hacker News это ~26 токенов на материал, ~30 с на 30 материалов);
- `dedup_hash` считается по оригиналу, поэтому перевод не может создать дубль;
- оригинал сохраняется в `extra` (`original_title`, `original_description`), так что
  перевод можно перепроверить или переделать позже;
- сбой перевода не теряет материал: он сохраняется на языке оригинала с пометкой
  `translation_failed` в `extra`;
- `keywords` раздела работают по переведённому тексту, поэтому для иностранного
  источника ключи надо задавать по-русски.

Целевой язык по умолчанию русский, меняется переменной `TRANSLATE_TO` (`rus`/`eng`).

## Конфигурация

Три файла, три ответственности:

| Файл | Отвечает за |
|---|---|
| `config/labels.yaml` | реестр меток: id, заголовок, эмодзи, порядок |
| `config/sources.yaml` | источники (транспорт), маппинг полей, правила дедупликации |
| `config/queries.yaml` | подписки: что и когда собирать, глубина, лимит, ключевые слова |

Добавить раздел = дописать метку в `labels.yaml` и повесить её на источник — код не меняется.
Добавить источник = блок в `sources.yaml`; поля описываются точечным путём
(`employer.name`, `vacancy.job-name`). Расписание — обычный cron:

```yaml
# Значения по умолчанию для всех запросов: запрос может переопределить любое
defaults:
  limit: 10
  lookback_days: 10        # глубина проверки, если запрос не задал свою
  summarize: false
  notify_empty: true

queries:
  - id: daily_news
    label: news
    schedule: "0 9 * * *"        # ежедневно в 9:00 (Europe/Moscow)
    limit: 10                    # переопределяет defaults
    keywords:
      any: ["ИИ", "нейросет", ["машинн", "обучени"]]
      exclude: ["промокод", "скидк"]
```

Настройки из `defaults` применяются ко всем запросам, а значение внутри запроса
переопределяет умолчание. Именно поэтому в конфиге видно два `lookback_days`:
`defaults.lookback_days` — глубина по умолчанию, а `lookback_days` у запроса —
своя глубина для этого раздела (например, у `daily_vacancies` она 3 дня, потому
что вакансии устаревают быстрее новостей).

**Проверка на старте.** Дубли ключей YAML отклоняются: PyYAML молча оставляет
только последнее значение, поэтому такой конфиг

```yaml
keywords:
  any: ["промпт"]
  any: ["python"]      # ← первое значение потеряется
```

приводит к понятной ошибке `ключ «any» записан дважды в одном объекте` вместо
молчаливой потери ключей. Заодно проверяются неизвестные метки, битый cron,
несуществующие источники и типы полей.

### Правила `keywords`

Ключевые слова — это **третий этап фильтрации**, самый поздний: они применяются при сборке
дайджеста, после того как материалы уже легли в базу. Поэтому по ним можно «передумывать»:
поменяли `keywords` — старые материалы в базе сразу отбираются по-новому, повторный сбор
не нужен. Отбор идёт **до** применения `limit`, то есть лимит не съедают отброшенные
материалы (кандидатов просматривается с запасом ×25).

Четыре ключа, каждый необязательный:

| Ключ | Смысл | Пример |
|---|---|---|
| `any` | пройдёт материал, если встретился **хотя бы один** | `any: ["нейросет", "ИИ"]` |
| `all` | нужны **все** элементы списка | `all: ["машинн", "обучени"]` |
| `exclude` | если встретился хоть один — материал **отбрасывается** | `exclude: ["промокод", "гороскоп"]` |
| `fields` | где искать; по умолчанию `title` и `description` | `fields: [title]` |

Порядок проверки: сначала `exclude`, затем `all`, затем `any`. То есть материал, который
одновременно попал под `exclude` и под `any`, будет отброшен — исключение сильнее.
Если `any` и `all` заданы вместе, работают оба условия.

#### Три правила поиска, о которые легко споткнуться

**1. Ключ короче 4 символов ищется по границам слова, длинный — по подстроке.**
Короткие ключи иначе дают ложные срабатывания: «ИИ» как подстрока совпадает с «Росс**ии**»,
«информац**ии**», «Туркмен**ии**». Поэтому:

```yaml
any: ["ИИ"]              # сработает на «ИИ» и «ии-агент», но не на «России»
any: ["нейросет"]        # длинный: поймает нейросеть, нейросети, нейросетевой
```

Регистр значения не имеет: и текст материала, и ключи перед сравнением приводятся
к нижнему регистру, так что «ИИ» и «ии» — один и тот же ключ.

**2. Морфологии нет — «склонения» добиваются усечёнными основами.**
Не пишите «нейросеть»: точная форма пропустит «нейросети» и «нейросетей». Пишите основу
без последних букв — `нейросет`, `разработ`, `уязвимост`, `инженер`. Это работает
и для русских слов, и для английских: `test` поймает `testing`, `tests`, `tester`.

У подстрочного поиска есть обратная сторона: он ловит и лишнее. `test` совпадёт
с «con**test**», `агент` — с «ре**агент**». Если раздел забит мусором, спасают либо
более длинные ключи, либо `exclude`:

```yaml
any: ["тестировани", "тестировщик"]     # точнее, чем "тест"
exclude: ["реагент", "контест"]         # или отсечь лишнее явно
```

**3. Фраза задаётся группой строк, а не пробелом.**
Ключ «машинное обучение» не сработает, если в тексте «машинного обучения».
Группа — это список внутри списка, в нём должны встретиться **все** слова:

```yaml
any:
  - "нейросет"
  - ["машинн", "обучени"]     # найдёт «машинного обучения», но не «машинное зрение»
  - ["речева", "модел"]       # и не «модель речи»
```

Одиночные короткие ключи в группе тоже работают по границам слова, поэтому
`["ии", "агент"]` ищет «ии-агент», но не «информации».

#### Как проверить ключи, не гадая

Если раздел пуст, запустите `/digest` — бот пришлёт отчёт с причиной, и одна из строк
будет про ключи:

```text
💼 Вакансии — сегодня нового нет
Проверено: материалов 100, в 2 источниках, записано в базу 60, повторов 0
Ключевые слова раздела: промпт
Ни один из 60 новых материалов не совпал с ключами
```

Это ровно тот случай, когда ключи слишком узкие: 60 материалов есть, а раздел пуст.

#### Ключи и перевод источников

Для источника с полем `translation` (см. ниже) ключи применяются **к переведённому
тексту**. Поэтому для Hacker News и подобных пишите русские основы: `агент`, `модел`,
`уязвимост`, а не `agent`, `model`, `vulnerability` — английские варианты уже не встретятся.

#### Готовый пример с комментариями

```yaml
queries:
  - id: daily_news
    label: news
    schedule: "0 9 * * *"
    lookback_days: 1
    limit: 10
    keywords:
      any:
        - "нейросет"                    # основа: любые словоформы
        - ["машинн", "обучени"]         # фраза из двух слов
        - "ИИ"                          # короткий — по границам слова
      exclude: ["промокод", "скидк", "гороскоп"]
      fields: [title, description]      # значение по умолчанию, можно не писать
```

### Один `lookback_days` — окно отбора, второй — глубина сбора

В конфиге два `lookback_days`, и это не дубль: у них разные роли.

**Окно отбора (у запроса).** `lookback_days` внутри запроса фильтрует материалы
при сборке дайджеста:

```sql
WHERE label = ? AND created_at >= ?     -- сегодня − lookback_days
```

Считается по **дате публикации материала**, а не по времени сбора: остановили
сервис на неделю, запустили — в окно попадут только свежие публикации, старые
не «всплывут». Каждый раздел отбирает по своему окну, независимо от других.

**Глубина сбора (у источника).** Источник не знает про разделы: ему задаётся одна
глубина — **максимум по запросам, которые его используют** (`lookback_for_source`).
Для источников с серверной фильтрацией эта глубина уходит прямо в запрос:
у GitHub подставляется в `created:>{since}`, у «Работы России» — в параметры API.

```text
daily_news           окно 10 дн.   →  tass_news, lenta_news, kommersant_news: сбор 10 дн.
daily_vacancies      окно  3 дн.   →  trudvsem_vacancies, habr_career: сбор 3 дн.
daily_tech           окно 10 дн.   →  habr, github_trending, hackernews: сбор 10 дн.
weekly_competitors   окно  7 дн.   →  vcru: сбор 7 дн.
```

Зачем максимум: если один источник обслуживает два раздела с окнами 3 и 7 дней,
собирать надо на 7 — иначе раздел с широким окном недополучит материалы. Сейчас
у каждого источника ровно один запрос, поэтому максимум ничего не меняет, но
правило действует заранее.

Менять эти значения стоит вместе: окно запроса не может быть шире того, что
собирает источник, иначе материалы просто не доедут до базы.

## Команды бота

| Команда | Действие |
|---|---|
| `/start`, `/help` | приветствие, разделы из реестра, список команд |
| `/digest` | немедленный сбор и дайджест по всем разделам |
| `/digest метка` | только по указанной метке, например `/digest news` |
| `/last [метка]` | последние материалы из базы, без обращения к источникам |
| `/labels` | разделы и количество записей |
| `/sources` | источники, их метки и статус последнего прогона |
| `/status` | последний запуск, размер базы, расписание, ближайшие срабатывания |
| `/clear` | очистить базу (материалы и историю дайджестов) — с подтверждением |
| `/clear дата1 [дата2]` | очистить только записи за период, например `/clear 2026-10-01 2026-10-05` |
| `/pause`, `/resume` | выключить или включить автозапуск |
| `/id` | ваш chat_id |

Доступ ограничен allowlist (`TG_CHAT_ID` и `TG_ALLOWED_CHAT_IDS`): токен бота находится
поиском, поэтому чужие чаты получают «Доступ ограничен», а в лог идёт предупреждение.

### Один прогон — одно сообщение

Все разделы одного прогона (`/digest`, `run_on_start`) уходят **одним сообщением**:
сначала шапка с датой и общим резюме, затем разделы с их заголовками.

```text
🗓 Дайджест за 12.10.2026

<общее резюме по всем разделам — 2–3 строки>

📰 Новости отрасли — 3
...
🛠 Обновления технологий — 10
...
🏢 Публикации конкурентов — 3
...
```

Резюме считается **по всем разделам сразу** и стоит в шапке, до первого раздела:
раньше оно относилось только к новостям и стояло под их заголовком, из-за чего весь
дайджест выглядел как «только новости». Для одного раздела работает обычный путь,
для нескольких — `DeepSeekSummarizer.summarize_sections`: он получает материалы,
сгруппированные по разделам, и обязан упомянуть каждый.

Так сделано ещё и потому, что серия из четырёх сообщений подряд склеивается Telegram
в одно уведомление: видимым остаётся только первый раздел. Если текст не влезает в
лимит Telegram, сообщение режется по границам разделов и материалов — разорванных
тегов не бывает, это проверяется тестом.

Cron-задачи разделов (`0 9`, `0 10`, `0 11`) идут каждая сама по себе: они и так
разнесены по времени, поэтому приходят отдельными сообщениями.

### Может не находить, но не может молчать

Пустой раздел — это тоже результат, поэтому он всегда приходит сообщением с причиной,
а не тишиной. Отчёт собирается из статистики каждого этапа отбора:

```text
💼 Вакансии — сегодня нового нет
🕒 12.10.2026 13:13 — по команде /digest vacancies
Проверено: материалов 100, в 2 источниках, записано в базу 0, повторов 60
Отсеяно при сборе: Работа России — открытые данные (40) — фильтры источника: зарплата, валюта
Все материалы уже были в базе (повторов 60)
Ключевые слова раздела: промпт
Глубже окна (3 дн.) в базе лежит материалов: 62, самый старый — 2025-11-07
Окно проверки: 3 дн.
```

Строка `🕒 …` показывает время и повод прогона: `по команде /digest`, `по расписанию`
или `при старте сервиса`. Без неё два отчёта об одном разделе с одинаковыми счётчиками
из разных часов выглядят как дубль, хотя это два честных прогона.

В отчёт попадает то, что важно для диагностики: сколько материалов отсеяли жёсткие
`item_filters` источника, сколько оказалось повторами, какие ключевые слова требует раздел,
и подсказка про `lookback_days`, если в базе лежат материалы старше окна. Если источник
упал, это сказано прямо («часть данных могла не дойти»), а не спрятано за «нового нет».

Отключается на уровне запроса (`notify_empty: false` в `defaults` или у конкретного запроса),
если по какой-то подписке пустые отчёты не нужны. По умолчанию включено для всех.

### Очистка базы (`/clear`)

Команда ничего не удаляет сразу: бот показывает, что и сколько будет удалено, и ждёт
подтверждения — кнопкой **«Да, очистить»** либо текстом **да** / **нет** (2 минуты, потом
подтверждение протухает). Даты принимаются как `ГГГГ-ММ-ДД`, так и `ДД.ММ.ГГГГ`; одна дата
означает один день, две — период **включительно**. Период считается по дате публикации
материала (`created_at`), а не по времени сбора.

Удаляются материалы вместе со связями в истории дайджестов; пустые шапки дайджестов
убираются. Подписки, их расписание, `is_active` и журнал прогонов источников не
затрагиваются, поэтому `/clear` не ломает бота и автозапуск. Удаление идёт пакетами под
общим writer-локом, а вызывается оно под `collection_lock` — одновременный сбор не
пересечётся с очисткой.

## Деплой на VPS (Coolify)

Схема проверена на Ubuntu 24.04 (2 vCPU, 4 ГБ RAM, 58 ГБ NVMe, дата-центр в Амстердаме)
с Coolify 4.5. Сервис headless: входящий HTTP-порт не слушает, поэтому домен, SSL и
обратный прокси не нужны.

### Что нужно

- VPS с Ubuntu 24 и публичным IP, root-доступ по SSH-ключу;
- репозиторий на GitHub с этим кодом;
- токен бота и ваш `chat_id`.

### Переменные окружения

Задаются в панели Coolify (`Environment Variables`); файл `.env` на сервере не нужен.

| Переменная | Обязательна | Значение |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | да | токен от @BotFather |
| `TG_CHAT_ID` | да | ваш chat_id |
| `GITHUB_TOKEN` | нет | поднимает лимит GitHub API (10 → 30 req/min) |
| `DEEPSEEK_API_KEY` | нет | включает перевод и саммари |
| `DEEPSEEK_MODEL` | нет | по умолчанию `deepseek-flash` |
| `TRANSLATE_TO` | нет | `rus` / `eng` |
| `TZ` | нет | `Europe/Moscow` — от него зависит cron |
| `LOG_LEVEL` | нет | `INFO` |
| `DRY_RUN` | нет | `false` |
| `TG_PROXY` | нет | только если Telegram недоступен из сети сервера |

### Установка на сервере

```bash
apt update && apt upgrade -y
apt install -y curl ufw git tmux
timedatectl set-timezone Europe/Moscow
ufw allow 22/tcp                      # до enable, иначе можно потерять SSH
ufw --force enable
curl -fsSL https://get.docker.com | sh
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | bash
```

Панель Coolify слушает порт `8000`. Публиковать его в интернет не нужно: `ufw` **не
фильтрует** порты, опубликованные Docker (DNAT идёт в цепочке `DOCKER` мимо правил
ufw), поэтому «закрыть через ufw» здесь не работает. Панель привязывается к loopback:

```bash
sed -i 's/8000:8000/127.0.0.1:8000:8000/' /data/coolify/source/docker-compose.yml
cd /data/coolify/source && docker compose up -d
```

и открывается через SSH-туннель:

```bash
ssh -i ~/.ssh/id_ed25519 -L 8000:127.0.0.1:8000 -N root@<IP_сервера>
# затем http://localhost:8000
```

Правку привязки нужно повторять после самообновления Coolify — он перегенерирует
`docker-compose.yml`. Проверка, что порт не торчит наружу (снаружи должен быть `000`):

```bash
curl -m 5 -o /dev/null -w '%{http_code}\n' http://<IP_сервера>:8000
```

Обратный прокси Coolify (`coolify-proxy`, Traefik на 80/443) проекту не нужен, его
можно остановить: `docker stop coolify-proxy && docker update --restart=no coolify-proxy`.

### Деплой

1. Coolify → `Keys & Tokens` → `Private Keys` → Add (RSA) → скопировать публичную часть.
2. GitHub → `Settings` → `Deploy keys` → Add deploy key → вставить ключ → `Allow write access`.
3. Coolify → New Project → Add → **Docker Compose**, ветка `main`, файл `/docker-compose.yml`.
4. Заполнить переменные из таблицы → **Deploy**.
5. В логах деплоя должны появиться `pipeline | [...] fetched=… new=… dup=…` и старт бота.

### Проверка

**Важно: в Coolify контейнер называется иначе.** Coolify игнорирует `container_name` из
`docker-compose.yml` и назначает своё имя вида `aggregator-<uuid>-<timestamp>`. Поэтому
имя надо получать командой:

```bash
CID=$(docker ps --filter 'name=aggregator' --format '{{.Names}}' | head -1)
echo "$CID"
```

Локально (`docker compose up -d`) работает обычное имя `news-vacancy-aggregator`.

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}'   # контейнер Up
docker logs -f "$CID"                                 # живой лог
```

В Telegram: `/start`, `/status` (время запуска и ближайшие cron-срабатывания — сдвиг
означал бы неверный `TZ`), `/digest news`.

### Резервное копирование и восстановление

Выполняется на сервере по SSH (в контейнере приложения Docker CLI нет).

```bash
# имя контейнера
CID=$(docker ps --filter 'name=aggregator' --format '{{.Names}}' | head -1)

# бэкап
docker cp "$CID":/app/data/aggregator.db /root/backup-$(date +%F).db
ls -lh /root/backup-*.db

# восстановление
docker cp /root/backup-2026-10-28.db "$CID":/app/data/aggregator.db
docker restart "$CID"
```

После восстановления `/status` должен показать прежний размер базы.

### Автодеплой

GitHub → `Settings` → `Webhooks` → Add webhook: URL и Secret берутся в Coolify на вкладке
`Webhooks` приложения, content type `application/json`, событие `Just the push event`.
Проверка: `git push` в `main` → в Coolify появляется новый deployment → бот перезапускается
с новым кодом. Пересборка занимает 30–60 секунд, бот в это время не отвечает; сообщения
не теряются — long polling дочитает их после старта.

### Сеть: что проверяли на этой схеме

С US-адреса доступны и `api.telegram.org`, и российские источники (`tass.ru`, `lenta.ru`,
`kommersant.ru`, `vc.ru`, `habr.com`, `trudvsem.ru`), поэтому `TG_PROXY` и отключение
источников не понадобились. Повторить проверку при смене дата-центра:

```bash
for u in https://api.telegram.org https://tass.ru/rss/v2.xml https://lenta.ru/rss/news \
         https://www.kommersant.ru/RSS/news.xml https://vc.ru/rss/all ; do
  printf '%-50s %s\n' "$u" "$(curl -sS -m 25 -o /dev/null -w '%{http_code}' "$u" 2>&1)"
done
```

## Особенности и ограничения

- **Telegram Bot API может быть недоступен** из российской сети: DNS резолвится, но TCP на 443
  не устанавливается. Варианты: VPN, переменная `TG_PROXY` (`socks5://` или `http://`),
  либо запуск на внешнем сервере через docker-compose. `TG_PROXY` применяется и к отправке
  дайджестов (`bot/sender.py`), и к поллингу бота (`bot/telegram_bot.py`): иначе доставка
  работала бы, а бот падал при старте. На европейском VPS (Амстердам) доставка проверена:
  `api.telegram.org` отвечает кодом `302`, `TG_PROXY` не нужен (см. раздел «Деплой на VPS»).
- **HeadHunter больше не источник**: публичный поиск вакансий закрыт, см. выше.
- **Медленные API**: открытые данные «Работы России» генерируют ответ 14–17 секунд независимо
  от размера страницы, поэтому у источника свой `timeout: 30` и одна страница за прогон.
- **Вежливость к источникам**: таймаут 10 с, три попытки с экспоненциальным backoff, учёт
  `Retry-After`, собственный User-Agent с контактом, последовательный обход источников.
- **Права и этика**: собираются только публичные данные, соблюдаются условия источников;
  секреты (`Подключение.txt`, `.env`) внесены в `.gitignore` и в репозиторий не попадают.
